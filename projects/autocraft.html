CASE STUDY / 03 · AUTOCRAFT

STATE
BEFORE SPEED.

Meteor Client automation for maximum-batch crafting. The relevant engineering problem is synchronization: one network mutation is followed by evidence before the next operation is allowed.

LANGUAGEJava
PLATFORMMinecraft · Meteor
PATTERNExplicit state machine
FAILURE POLICYPause, don't guess
01 / PROBLEM

FAST AUTOMATION BECOMES WRONG AUTOMATION WHEN STATE DRIFTS.

A naïve crafting loop can issue clicks faster than server/container state is acknowledged. That creates stale assumptions: wrong cursor contents, unexpected crafting-grid contents, duplicate operations or interaction against a changed menu.

BoneFactory instead models the operation as discrete states and makes acknowledgement a boundary that local speed settings cannot bypass.

VALIDATE_CONTEXT → SELECT_BATCH → PLACE_RECIPE → WAIT_RECIPE_ACK → DROP_RESULT → WAIT_DROP_ACK → SELECT_BATCH Side states: WAIT_INPUT PAUSED
02 / ACK BOUNDARY

ONE NETWORK MUTATION. THEN EVIDENCE.

PLACE

Recipe placement waits.

The module checks expected result/grid or input mutation plus container advancement before moving to the drop state.

DROP

Whole-result drop waits.

The next batch does not begin until result slot and crafting grid reach the expected empty state.

TIMEOUT

40 ticks, then pause.

Missing acknowledgement leads to PAUSED instead of blindly replaying the same network mutation.

SPEED

Local speed remains bounded.

x1/x3/x5/x10 affects local transitions only. It does not permit a second network mutation while one is unacknowledged.

03 / SAFETY

EXTERNAL STATE IS NOT TREATED AS MINE.

CURSOR

Non-empty cursor pauses.

The addon will not move or drop an item already held by the user or another interaction.

GRID

Unexpected contents pause.

Unowned crafting contents are treated as unsafe rather than overwritten.

CONTAINER

Menu identity is tracked.

A changed container triggers initialization rather than continuing with stale assumptions.

WORLD

Session change resets state.

Join, leave and world changes clear runtime transaction state before automation proceeds.

04 / THROUGHPUT

NATIVE MAXIMUM OPERATIONS, NOT PER-RESULT SPAM.

CraftingService plans the maximum craftable batch, uses Minecraft's native maximum recipe placement and performs one native whole-result THROW against the result slot.

USE_MAX_ITEMS = true placeRecipeMax(...) → wait for server/menu acknowledgement WHOLE_RESULT_DROP_INPUT = THROW dropWholeResult(...) → wait for server/menu acknowledgement

This avoids inventing cursor-deposit logic and per-result click loops while keeping synchronization explicit.
