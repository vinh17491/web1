CASE STUDY / 03

AutoCraft
state before speed.

A Meteor Client addon for Minecraft Java Edition that automates maximum-batch crafting. The engineering focus is synchronization: network mutations are serialized around server acknowledgement and the module pauses when context is unsafe.

LanguageJava
PlatformMinecraft · Meteor
PatternExplicit state machine
Failure policyPause, do not guess

01 / PROBLEM

Fast automation becomes wrong automation when state drifts.

A naïve crafting bot can spam clicks faster than server/container state is acknowledged. That creates stale assumptions: wrong cursor contents, unexpected crafting-grid contents, duplicated operations or interaction against a changed menu.

BoneFactory instead models the operation as discrete states and treats acknowledgement as a boundary that local speed settings cannot bypass.

02 / STATE MACHINE

One network mutation, then evidence.

VALIDATE_CONTEXT → SELECT_BATCH → PLACE_RECIPE → WAIT_RECIPE_ACK → DROP_RESULT → WAIT_DROP_ACK → SELECT_BATCH Side states: WAIT_INPUT PAUSED
ACK

Recipe placement waits

The module checks expected result/grid or input mutation plus container state advancement before moving to the result drop.

ACK

Drop waits

After whole-result drop, the next batch does not start until the result slot and crafting grid reach the expected empty state.

TIMEOUT

40-tick acknowledgement timeout

Missing acknowledgement leads to PAUSED instead of repeated blind mutation.

SPEED

Local speed is bounded

x1/x3/x5/x10 changes local transition budget only. It does not permit another network mutation while one is awaiting acknowledgement.

03 / SAFETY INVARIANTS

External state is not treated as mine.

CURSOR

Non-empty cursor pauses

The addon will not move or drop an item already held by the user or another interaction.

GRID

Unexpected contents pause

A non-empty result/grid outside the owned transaction is treated as unsafe rather than overwritten.

CONTAINER

Menu identity is tracked

A changed container triggers initialization instead of continuing with stale assumptions.

WORLD

World/session change resets runtime

Join/leave/world-change events clear transaction state before automation continues.

04 / THROUGHPUT

Use native maximum operations instead of per-result loops.

CraftingService plans the maximum craftable batch from inventory/grid input, uses Minecraft’s native max-recipe placement and performs one native whole-result THROW operation on the result slot.

USE_MAX_ITEMS = true placeRecipeMax(...) → wait for server/menu acknowledgement WHOLE_RESULT_DROP_INPUT = THROW dropWholeResult(...) → wait for server/menu acknowledgement

This reduces cursor deposits, inventory-destination logic and per-result click loops while keeping the synchronization boundary explicit.

05 / ENGINEERING SIGNAL

Why this belongs in a software portfolio.

The domain happens to be a game client, but the relevant engineering concerns are general: state machines, remote acknowledgement, stale state, invariants, timeouts, bounded throughput and safe recovery.

Boundary

This is client automation, not a distributed-systems benchmark. The case study claims the synchronization behavior visible in source and no more.
