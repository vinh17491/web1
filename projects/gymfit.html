CASE STUDY / 01

GymFit
system over screen.

Full-stack gym management and commerce platform. This case study focuses on the engineering surfaces that can be audited: backend authority, session security, ownership checks, inventory invariants, state transitions, migrations and acceptance evidence.

RoleFull-stack engineering
StackReact · TypeScript · Express
DataSQL Server
StatusIn progress

01 / PROBLEM

Multiple roles, one authoritative backend.

GymFit combines public catalog flows with authenticated Member, Coach and Admin workflows. The hard part is not rendering three dashboards; it is keeping authorization, ownership, inventory and order/payment state correct across those surfaces.

The implementation treats frontend guards as navigation UX only. API middleware and ownership queries remain authoritative, so changing a URL or client-side state is not enough to widen access.

Scope honesty

The project is still in progress. Workout-program TASK-008 was documented separately and was not represented as complete in the audited baseline.

03 / SECURITY

JWT was not treated as “login solved.”

The hardened auth flow validates signature, issuer, audience, user/session state, token version and current role before route authorization. Refresh credentials are opaque random values stored as hashes.

Access token → signature / issuer / audience → live AuthSession + user token_version / role / active state → route role check → ownership query Refresh token → opaque credential → SHA-256 hash in DB → atomic rotation → replay detection → token-family revocation
REVOCATION

Logout and security changes matter

Session records allow logout and password/security changes to revoke server-side access instead of relying only on token expiry.

IDOR

Cross-owner access tested

Acceptance differentiates separate Member and Coach accounts to verify self/assigned scope instead of testing only role names.

04 / COMMERCE

Inventory is a state invariant, not a number on a card.

Catalog data separates Product and ProductVariant. Inventory is tracked per variant, and availability is derived from on-hand stock minus reservations.

available = on_hand - reserved Product → Variant → Cart → Checkout → Order ↓ Reservation ↓ Payment ↓ Fulfillment Order: PENDING → CONFIRMED → PROCESSING → SHIPPED → DELIVERED Payment: UNPAID → PENDING → PAID / FAILED → REFUNDED

Order creation reserves stock. Valid cancellation or expiration releases reservations. Delivery reduces both reserved and on-hand quantities. Order/payment history records actor, transition and time.

RUNTIME

BUILD

Build gates recorded

Backend build/typecheck and lint, frontend TypeScript and production build were recorded as pass, with warnings preserved rather than hidden.

CLEANUP

Acceptance data isolated

Acceptance resources were cleaned and canonical database integrity was checked instead of leaving test fixtures mixed into the primary state.

06 / LIMITATIONS

What I would not claim.

Current boundaries

Bank settlement/refunds are manual records rather than Stripe/bank settlement APIs; some legacy modules retain mixed controller/service patterns; strict CSP/exact CORS and a future cookie-based auth model remain improvement areas. These are documented constraints, not hidden production claims.

The point of exposing limitations is not self-criticism. It makes the engineering boundary reviewable and prevents a demo project from pretending to be a production platform it is not.
