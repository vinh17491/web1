React/Vite client with an ASP.NET Core API. The engineering signal is not an airline-themed screen; it is explicit authentication, persistence and checkout/payment responsibilities that can be inspected separately.

01 / SYSTEM

A CLIENT / API APPLICATION, NOT A STATIC MOCK.

The backend registers controllers, React CORS origins, Swagger/OpenAPI with Bearer authentication, an EF Core DbContext and explicit scoped services for checkout and payment workflow.

React 19 / Vite → Axios → ASP.NET Core controllers → checkout + payment services → Entity Framework Core → SQLite

Aviation reference image used as visual context; the engineering claims are linked to source separately.

02 / SERVICE BOUNDARIES

CHECKOUT DOES NOT HAVE TO LIVE INSIDE ONE GIANT CONTROLLER.

VALIDATION

CheckoutValidationService

Owns precondition checks before creation and keeps them out of HTTP plumbing.

CREATION

CheckoutCreationService

Separates persistence and booking creation behavior from the controller surface.

SUMMARY

CheckoutSummaryService

Provides a dedicated boundary for assembling checkout summary state.

FINALIZATION

PaymentFinalizationService

Payment finalization is isolated rather than mixed into unrelated request handling.

The project also contains BookingPaymentClosureService and PaymentSimulationService, which makes the current payment boundary explicit.

03 / AUTH

JWT VALIDATION IS EXPLICIT.

JWT Bearer → validate issuer → validate audience → validate lifetime → validate signing key → ASP.NET Core authorization Swagger / OpenAPI → Bearer security definition → authenticated endpoint testing

The JWT key is required from configuration and the source explicitly points toward user-secrets rather than hard-coding the credential in Program.cs.

04 / HONEST BOUNDARY

WHAT THIS PROJECT PROVES — AND WHAT IT DOESN'T.

PROVES

Full-stack integration.

React/Vite and ASP.NET Core are wired as distinct client/backend surfaces with CORS, authenticated API access and relational persistence.

PROVES

Workflow decomposition.

Checkout/payment concerns are separated into services that can be reasoned about independently.

BOUNDARY

Payment is a project simulation.

The repository contains PaymentSimulationService. This portfolio does not relabel that as Stripe or production bank settlement.

NEXT

Concurrency needs proof.

A real production seat-booking claim would require demonstrated uniqueness/locking/idempotency behavior. I do not claim that without evidence.
