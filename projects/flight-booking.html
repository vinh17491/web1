CASE STUDY / 02

Flight Booking
workflow boundaries.

A flight-booking application with a React/Vite client and ASP.NET Core backend. The useful signal here is not “airline UI”; it is how authentication, persistence, checkout validation, creation, summary and payment concerns are separated.

FrontendReact 19 · Vite
BackendASP.NET Core
PersistenceEF Core · SQLite
AuthJWT Bearer

01 / SYSTEM

A client/API application, not a single-page mock.

The backend registers controllers, CORS for the React client, Swagger/OpenAPI with Bearer authentication, an EF Core DbContext and explicit scoped services for checkout and payment workflow.

02 / SERVICE BOUNDARIES

Checkout is split into responsibilities.

The current backend exposes separate services rather than pushing the full workflow into one controller:

VALIDATION

CheckoutValidationService

Owns precondition checks before creating checkout state.

CREATION

CheckoutCreationService

Separates creation behavior from HTTP request plumbing.

SUMMARY

CheckoutSummaryService

Provides a dedicated boundary for checkout summary behavior.

FINALIZATION

PaymentFinalizationService

Payment finalization is isolated from the controller surface.

There is also a BookingPaymentClosureService and a PaymentSimulationService, making the project’s payment boundary explicit.

03 / AUTH

Authenticated API surface with explicit validation.

JWT Bearer → validate issuer → validate audience → validate lifetime → validate signing key → ASP.NET Core authorization Swagger/OpenAPI → Bearer security definition → authenticated endpoint testing

The JWT key is required from configuration and the source explicitly recommends user-secrets instead of hard-coding it in Program.cs.

04 / DECISION QUALITY

What this project proves — and what it does not.

PROVES

Full-stack integration

React/Vite and ASP.NET Core are wired as separate frontend/backend surfaces with explicit CORS, API access and persistence.

PROVES

Workflow decomposition

Checkout/payment concerns are factored into services that can be reasoned about separately from controllers.

BOUNDARY

Payment is not represented as a real processor

The repository contains PaymentSimulationService. This portfolio therefore describes it as a project payment simulation, not Stripe/bank production settlement.

NEXT

Concurrency deserves explicit proof

A production seat-booking claim would require demonstrated locking/uniqueness/idempotency behavior. I do not claim that here without evidence.
